# Lumenverba 临时 Agent 维护交接设计

日期：2026-08-17

## 1. 背景

Lumenverba image 的主维护、版本判断、真实 API 测试、PR 合并、标签和 Release 决策由主维护 Agent 负责。其他 Agent 只在明确授权的范围内，临时承担脚本代码维护或小型优化。

当前功能分支为 `codex/gpt-image-2-flexible-sizes`，PR #4 尚未合并，RC 标签为 `v1.2.6-rc.1`。临时 Agent 需要足够的项目上下文，但不能获得把独立副本直接变成发布源的权限。

## 2. 目标

- 为临时 Agent 提供可追踪、可销毁、与主工作树隔离的维护环境。
- 把项目结构、代码契约、测试门禁和发布边界放入 Git 跟踪的维护文档。
- 让每次临时维护都通过分支、提交 SHA 和验证证据交付。
- 保持 GitHub 仓库、主维护分支和版本标签为唯一权威来源。
- 不暴露或复制 `LUMENVERBA_API_KEY`、真实回执和非必要生成图片。

## 3. 非目标

- 不创建第二个长期权威仓库。
- 不让临时 Agent 自动合并 PR、移动标签、创建 Release 或 force-push。
- 不在本次设计阶段修改 `lumenverba_image.py`、现有 `SKILL.md` 或版本元数据。
- 不把 `.git/worktrees` 内部目录当作交接目录。

## 4. 方案比较

### 方案 A：专用 Git clone（推荐）

每次维护任务从远端仓库 clone 到固定的临时维护目录，再从指定基线创建 `codex/` 任务分支。优点是 Git 历史、远端引用和清理边界清晰，适合把任务交给不同 Agent；缺点是占用少量磁盘并需要一次 clone/fetch。

### 方案 B：Git worktree

从现有仓库创建额外 worktree。优点是快速且共享对象库；缺点是依赖主仓库的 `.git/worktrees` 管理状态，宿主环境清理或路径失效时不适合作为长期交接目录。只用于本机短期任务。

### 方案 C：普通文件夹复制

不推荐。复制物不自然携带分支、标签、远端和提交关系，容易产生版本漂移，也容易把临时输出或凭据带入副本。

## 5. 推荐架构

### 权威层

- GitHub 仓库：`https://github.com/yixixi-yahaha/lumenverba-image`
- `origin/main`：正式集成基线。
- PR：唯一的代码审查和合并入口。
- 标签：不可移动的版本快照；RC 后续变化使用新 RC 标签。

### 临时实现层

默认维护 clone 路径建议为 `C:\Projects\lumenverba-image-agent-maintenance`，实际路径可由主维护 Agent 在任务开始时指定。每个任务都创建独立分支，例如 `codex/temp-fix-size-validation`。

临时 Agent 只在该 clone 和任务分支中工作，不直接修改主工作树，不直接在 `main` 上提交。

### 文档层

将以下文件提交到仓库，作为所有 Agent 的共同入口：

- `AGENTS.md`：全局维护规则、权限边界和不可违反的安全约束。
- `docs/maintenance/HANDOFF.md`：项目地图、当前版本、分支/PR 状态、关键契约和接管流程。
- `docs/maintenance/VERIFICATION.md`：离线测试、CLI 帮助、编译、差异检查、凭据扫描和可选真实 API 门禁。

文档只描述可复用规则，不记录某次 Agent 的聊天过程、密钥、临时回执或机器私有绝对路径。

## 6. 任务生命周期

1. 主维护 Agent 指定基线、范围、验收标准和是否允许真实 API。
2. 从远端 clone 或创建短期 worktree。
3. 从指定基线创建 `codex/` 任务分支。
4. 临时 Agent 先阅读 `AGENTS.md`、`CONTEXT.md`、`HANDOFF.md`、`VERIFICATION.md`、相关设计/计划和目标脚本。
5. 运行基线测试并记录结果；基线失败时停止并报告，不把旧问题混入新修复。
6. 只修改授权范围内的代码和测试；不修改密钥、发布元数据或无关文件。
7. 提交后报告提交 SHA、变更文件、测试命令和结果、未解决风险。
8. 主维护 Agent 独立审查 diff，必要时要求修复或 cherry-pick 到主维护分支。
9. 只有主维护 Agent 获得明确授权后，才执行 push、PR 更新、合并、标签或 Release。
10. 任务结束后保留 PR 所需分支；废弃任务则删除临时 clone/worktree 和任务分支，保留 GitHub 审计记录。

## 7. 权限边界

默认允许：读取仓库、修改授权脚本和测试、运行离线测试、创建本地任务提交。

默认禁止：读取或输出 API key、提交真实密钥、自动调用计费 API、重复创建请求、force-push、修改或覆盖既有标签、合并 PR、创建 Release、删除主分支或清理主维护工作树。

真实 API 测试必须单独授权，使用低额度单请求、唯一临时回执、结构化路径校验；创建请求失败或结果状态未知时不得盲目重试。

## 8. Lumenverba 当前契约摘要

- 只支持 `gpt-image-2`。
- 默认 `size=auto`、`quality=medium`。
- 自定义尺寸最长边不超过 3840，两边为 16 的倍数，比例不超过 3:1，总像素为 655,360 到 8,294,400。
- 显式尺寸超过 3,686,400 总像素时警告但允许执行。
- `quality` 仅支持 `low`、`medium`、`high`、`auto`；不兼容 `standard`。
- 回执中的每个返回路径都必须校验存在性和 PNG 签名并交付；数量不一致时保留全部返回路径并报告 `partial`。

## 9. 验收标准

- 临时 Agent 能从干净 clone 复现当前分支和标签关系。
- 文档明确指出主维护 Agent 是合并、版本和发布决策者。
- 离线测试、编译、CLI 帮助和凭据扫描命令可直接运行。
- 任务交付包含可验证的提交 SHA 和测试证据。
- 无密钥、真实回执、机器私有路径或不可追踪的普通文件夹副本进入 Git。
- 现有主工作树的用户改动不被覆盖，PR #4 和 `v1.2.6-rc.1` 不被移动。

## 10. 设计结论

采用“仓库内维护文档 + 每任务专用 Git clone/分支 + 主维护 Agent 审查”的组合。Git worktree 仅作为本机短期加速手段，普通文件夹复制不作为维护方式。实现阶段先添加三份维护文档和必要的忽略规则，再用一个无网络、无密钥的接管演练验证流程。
